why it exists

Every warehouse team needs the same answer about a product

Owns SKU-level product master data for the whole fleet: the handling classification (hazmat, fragile, temperature-sensitive, oversized, high value, DOT hazard class), the declared-versus-measured physical profile (unit dimensions and weight), and the packaging hierarchy (EACH -> INNER -> CASE -> PALLET with GS1 GTINs, eaches as the ledger unit)…

Today

It registers SKUs, classifies hazmat or fragile goods, tracks declared versus measured size, and manages GS1 pack levels.

The catch

The packaging decision still reads 'nothing built' though it shipped, reports via Kong are unverified, and nothing is authenticated.

Owns SKU-level product master data for the whole fleet: the handling classification (hazmat, fragile, temperature-sensitive, oversized, high value, DOT hazard class), the declared-versus-measured physical profile (unit dimensions and weight), and the packaging hierarchy (EACH -> INNER -> CASE -> PALLET with GS1 GTINs, eaches as the ledger unit). It is a pure producer: 8 CloudEvents flow out through a transactional outbox and six sibling contexts keep local event-fed copies; nothing flows in and no live cross-context calls exist in either direction. Study project practicing DDD and hexagonal architecture within the warehouse-systems fleet.
what it does

Handling, size and packaging live in one record per SKU

SKU registration

Every product starts with an explicit registration, guarded against races.

Handling classification

Hazmat, fragile, cold-chain and high-value rules are checked on entry.

Physical profile

Declared and measured sizes are kept, with big gaps flagged for stewards.

Packaging and GTINs

Each, inner, case and pallet levels carry validated GS1 GTINs.

Reliable event fan-out

An outbox mints one event per change for integration and analytics.

Data-quality reports

Daily fill-in counts, open discrepancies and coverage show data health.

warehouse-systems · executive briefing · November 2026product-master
SKU registration and lifecycle: register a product by SKU (PUT, aggregate version guards writes with optimistic concurrency); attributes of an unknown SKU are a 404 - master data has an explicit beginning Handling classification: closed set of handling tags (Hazmat, Fragile, TemperatureSensitive, Oversized, HighValue), TemperatureClass required iff TemperatureSensitive, DOTHazardClass 1-9 only with Hazmat; invariants moved unchanged from inventory-storage (ADR 0001/0003) Physical profile: declared vs measured unit dimensions/weight in integer mm and g; effective = measured else declared; latest measurement wins by measuredAt (409 stale-measurement); >10% declared-vs-measured discrepancy flagged for stewards (ADR 0002) Packaging hierarchy with GS1 GTINs: pack levels EACH/INNER/CASE/PALLET, GTIN-14 normalisation with mod-10 validation, GS1 immutability (changed case quantity = new GTIN, old level end-dated and kept resolvable), idempotent retirement, GTIN resolution endpoint GET /gtins/{gtin} (ADR 0011) Event publication via transactional outbox: one CloudEvents id minted per occurrence; unit events fan out to BOTH the integration topic and the analytics topic as two outbox rows in the use case's transaction (ADR 0004/0006) Master-data-quality analytics read side: projector consumes the analytics topic into a separate analytical DB (product_facts + profile_states), reports binary serves per-day fill-in counts, open discrepancies, coverage ratios and freshness (ADR 0006) Multi-protocol driving adapters over the same use cases: REST for operators/console, 8 MCP tools for agents, and an A2A agent (product_profile read, declare_pack_level write) for goal delegation - delegation only, never data sync (ADR 0005/0012) Operator micro-frontend productmaster_mfe: product list, register, detail and a Packaging screen (declare/retire levels, GTIN lookup), mounted by the console shell at /product-master/*
